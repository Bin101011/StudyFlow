## 세션 1

### 단계 1: 빈칸 클릭

**정한 내용**
- 빈칸을 눌러 만드는 계획의 기본 길이는 30분이다. 할 일을 끌어다 놓을 때는 1시간 그대로 둔다.
- 시작 시간은 어느 배율에서든 누른 곳에서 가장 가까운 5분으로 맞춘다. 끌어서 새 계획을 만들 때의 시작점도 같은 규칙을 쓴다.
- 만들어진 계획을 끌어서 옮기는 단위(5분 또는 15분)는 그대로 둔다.

**알아 둘 점**
- 문제의 원인: `timelineGrid`의 `pointerdown`이 `floorSnap`으로 내림한다. 1시간이 120px 미만이면 15분 단위라서, 16:44를 눌러도 16:30에서 시작한다. 사용자의 배율은 99px이다.
- `TL_DEFAULT_LENGTH`는 할 일 끌어다 놓기도 쓰므로 빈칸 클릭용 상수를 따로 만든다.
- 최소 배율(36px)에서는 30분이 18px이라 제목 입력 칸이 잘릴 수 있다. 입력하는 동안만 최소 높이를 보장한다.
- `tl_test`의 "1시간", "09:00으로 내림" 확인을 새 규칙에 맞춰 고친다.

**구현 결과 (2026-11-06, 끝남)**

`static/app.js`
- 상수 `TL_CLICK_LENGTH`(30분)와 `TL_CREATE_START_STEP`(5분)을 새로 만들었다. `TL_DEFAULT_LENGTH`(60분)는 할 일을 끌어다 놓을 때만 쓴다.
- `timelineGrid`의 `pointerdown`: 누른 자리(`anchor`)를 `floorSnap` 대신 가장 가까운 5분으로 맞춘다. 16:44를 누르면 16:45다.
- 끌어서 만들 때: 아래로 끌면 `anchor`가 시작, 위로 끌면 `anchor`가 끝이다. 끌고 있는 쪽 끝만 지금 단위(5분 또는 15분)에 맞춘다. 16:44에서 17:20까지 끌면 16:45–17:30, 16:20까지 끌면 16:15–16:45다. 최소 길이는 지금 단위이고, 하루 밖으로 나가면 잘라도 최소 길이를 지킨다.
- 하루 끝을 누르면 30분을 지키려고 시작을 당긴다. 23:50을 누르면 23:30–24:00이다. 계획에 없던 경우라 예전 방식을 따랐다.
- `openPlanCreator`: 제목을 쓰는 동안 블록에 `tl-typing` 클래스를 붙인다.
- `makePlanBlock`: 시간 표시 조건을 "45분 이상"에서 "블록 높이 44px(`TL_TWO_LINES_PX`) 이상"으로 바꿨다. 기본 길이를 30분으로 줄이자 새 계획에 시간이 안 보이게 되어서, 단계 4의 일부를 앞당겨 고쳤다.

`static/style.css`
- `.tl-creating.tl-typing { min-height: 30px; }`: 쓰는 동안만 최소 높이를 보장한다. 36px 배율의 30분은 18px이다. 저장하면 실제 길이로 그려진다.
- `.tl-creating .tl-title-input { padding: 2px 6px; }`: `input[type="text"]` 공통 규칙이 `.tl-title-input`보다 우선순위가 높아 작은 여백이 처음부터 적용되지 않았고, 입력 칸이 29px로 그려졌다. 새 계획 블록 안에서만 여백을 줄였다. 계획 작은 창의 입력 칸은 그대로다.

`tests/browser/tl_test.mjs`
- 30분과 가까운 5분 규칙에 맞춰 기대값을 고쳤다. 마우스 위치가 1px쯤 어긋날 수 있어 09:05, 13:02 등을 누르던 곳을 09:01, 13:01 등으로 옮겼다.
- 더한 검사: 16:44 클릭, 위아래 끌기, 입력 칸이 블록 안에 들어가는지(64px, 36px, 하루 끝), 99px와 64px에서 시간 표시.

시험과 확인
- `tl_test` 135개 모두 통과. 시간표에서 계획을 만드는 시험은 이것뿐이라 다른 시험은 돌리지 않았다.
- 고치는 도중 한 번, D 구간에서 시험용 브라우저가 20초간 응답하지 않아 시험이 멈췄다. 같은 코드로 다시 돌리니 통과했고 원인은 확인하지 못했다.
- 사용자가 진짜 앱에서 동작을 확인했다(2026-11-06).

### 단계 2: 너비 슬라이더

**정한 내용**
- 시간표 너비는 300~500px이다. 기본값 400은 그대로 둔다.
- 오른쪽 칸 너비 슬라이더를 새로 만든다. 300~450px이고 기본값은 300이다. 범위는 직접 써 보며 고칠 수 있다.
- 두 값의 합은 850px을 넘지 못한다. 넘는 쪽으로 끌면 그 자리에서 막힌다. 예: 오른쪽이 450이면 시간표는 400까지만 간다.

**알아 둘 점**
- `style.css`의 `.today-layout` 최솟값 330px도 낮춰야 300~320px이 실제로 적용된다.
- `.mini-calendar`의 `max-width: 300px`을 풀어야 달력도 함께 넓어진다.
- 슬라이더의 `max` 속성을 바꾸면 눈금이 다시 계산돼 손잡이가 튄다. `max`는 두고 `input` 처리에서 값을 한계로 되돌린다.
- 합계 제한은 `clean_settings`에도 넣어 저장 파일이 잘못된 값을 갖지 않게 한다.
- 창이 좁으면(1100px 미만) 배치가 달라져 오른쪽 칸이 아래로 내려간다. 이때 슬라이더가 레이아웃을 깨지 않는지 확인한다.

**구현 결과 (2026-11-06)**

`settings_store.py`, `app.py`
- `timelineWidth` 범위를 300~500으로 바꾸고 `todayRightWidth`(300~450, 기본 300)를 더했다. 합계 한계는 `TODAY_WIDTHS_MAX`(850) 하나로 두고, `GET /api/settings`의 `todayWidthsMax`로 화면에 알려 준다.
- `clean_settings`: 합이 850을 넘으면 오른쪽 칸만 보낸 경우 그 값을, 그 밖에는(둘 다 보냈거나 파일을 읽는 중) 시간표 너비를 줄인다. 옛 파일의 550은 먼저 500으로 맞춘 뒤 이 검사를 받는다. 지금 값 380은 범위 안이라 그대로다.

`static/app.js`
- `SETTING_CSS_VARS`에 `todayRightWidth`(`--today-right-width`)를 더했다.
- `limitSliderValue`: 슬라이더 `input` 처리에서 값을 한계로 되돌린다. `max` 속성은 바꾸지 않는다. 다른 슬라이더는 그대로 지나간다.

`static/style.css`
- `.today-layout`: 시간표 최솟값을 330px에서 300px로 낮추고, 오른쪽 칸의 최댓값을 `--today-right-width`로 바꿨다. 창이 좁을 때 오른쪽 칸이 250px까지 줄어드는 것은 그대로다.
- `.mini-calendar`: `max-width`를 고정 300px에서 `--today-right-width`로 바꿨다. 없애지 않은 이유는 좁은 창에서 오른쪽 칸이 줄 전체를 쓸 때 달력이 끝까지 늘어나기 때문이다.

`templates/index.html`: 설정 탭의 안내 문구에 오른쪽 칸과 850px 한계를 적었다.

시험
- `test_settings_api`에 범위, 합계 한계, 옛 파일 값 검사를 더했다.
- `tl_test`에 M 구간을 더했다. 실제 마우스로 슬라이더를 끌어 양쪽 방향의 막힘, 막힌 뒤 되돌아오기, 저장, 실제 칸 너비, 좁은 창, [기본값으로]를 본다.

### 단계 3: 기본값 설정

**정한 내용**
- 시간표 첫 위치를 설정할 수 있게 한다. 기본은 17:00이 가운데에 오는 것이다.
- 일정 추가 기본 시간을 "종일" 또는 특정 시각(예: 16:45)으로 정할 수 있게 한다. **월간 보기에서 날짜를 누를 때만** 적용한다. 주간·일간 보기는 누른 시각을 그대로 쓴다.

**알아 둘 점**
- 지금 `scrollTimelineToDefault`는 오늘 날짜면 현재 시각을 위에서 1/3 지점에, 다른 날이면 07:00을 맨 위에 놓는다. 오전 9시 고정은 코드에 없다.
- `showDay`가 `needScroll`을 세우므로 날짜를 넘길 때도 같은 위치로 간다.
- 일정 추가는 `openAddDialog`의 월간 보기 부분만 바꾼다. 설정을 불러오기 전이면 지금 값(09:00)을 쓴다.
- 일정 기본 길이(지금 1시간)를 설정에 넣을지는 구현할 때 사용자에게 확인한다. → 2026-11-08 사용자가 넣기로 했다.

**구현 결과 (2026-11-08)**

`settings_store.py`
- 새 설정 3개: `timelineCenterTime`(기본 "17:00"), `eventDefaultStart`("09:00" 같은 시각 또는 "allDay", 기본 "09:00"), `eventDefaultMinutes`(15·30·60·90·120·180 중 하나, 기본 60. 일정 창의 길이 버튼과 같은 값).
- `clean_settings`: 시각은 `HH:MM` 모양(`TIME_TEXT_PATTERN`, 00:00~23:59)만 받는다. 틀린 값이면 원래 값을 지킨다.

`static/app.js`
- `scrollTimelineToDefault`: 오늘이든 다른 날이든 설정 시각을 칸 가운데에 놓는다. 예전의 "오늘은 지금 시각을 위에서 1/3, 다른 날은 07:00을 맨 위"는 없앴다. 위쪽 여백 `TL_SCROLL_PAD`도 계산에 넣는다.
- 시험에서 찾은 문제: 가운데로 맞춘 뒤 일정이 늦게 도착해 시간표 위에 종일 일정 줄이 생기면 칸이 줄어 가운데가 위로 밀렸다(17:00이 16:37). `timelineCenterHold`와 `ResizeObserver`로, 사용자가 아직 시간표를 스크롤하거나 누르지 않았으면 칸 높이가 바뀔 때 다시 가운데로 맞춘다. 끄는 중에는 맞추지 않는다.
- `openAddDialog`: 월간 보기는 `eventDefaultStart`(종일이면 종일 일정 창, 숨은 시각은 09:00)로 시작한다. 길이는 월간·주간·일간 모두 `eventDefaultMinutes`다. 주간·일간의 종일 줄을 누르는 경우는 그대로다. 설정을 불러오기 전에는 09:00, 60분을 쓴다.
- 설정 탭의 시각 칸은 `setupSettingTimeInput`으로 연결했다. 칸을 떠나거나 Enter를 누르면 `normalizeTimeInput`으로 정리하고(1645, 4:45pm, 오후 4시 45분 등), 읽을 수 없으면 빨간 칸으로 알리고 저장하지 않는다.
- 오늘 탭 [기본값으로]는 시간표 첫 위치도 17:00으로 되돌린다.

`templates/index.html`, `static/style.css`
- "일정 추가" 칸: 월간 보기의 기본 시작(종일 체크 + 시각 칸), 새 일정 기본 길이(선택 칸), 안내 문구.
- "오늘 탭" 칸: 시간표 첫 위치(시각 칸).
- `.settings-time`(너비 80px, 빨간 칸 모양은 일정 창의 시간 칸과 같다).

시험
- `test_settings_api`: 기본값, 맞는 값, 틀린 값(24:00, 9:00, 45분, 앞뒤 글자, null, true).
- `tl_test` N 구간: 설정 칸에 실제로 입력해 저장, 시간표 가운데 위치(오늘, 날짜 넘김, 종일 줄이 늦게 생겨도), 스크롤한 뒤에는 저절로 안 움직임, 일정 추가 창 값(월간, 주간, 종일), 새로 불러온 뒤 칸의 값, [기본값으로]. H 구간의 "내일: 07:00이 맨 위"는 "17:00이 가운데"로 바꿨다.

## 세션 2

### 단계 4: 블록 글자

**정한 내용**
- 시간 표시 여부를 분이 아니라 실제 블록 높이로 정한다.
- 두 줄이 들어가면 제목 아래에 시간을 둔다. 안 들어가면 **제목 옆에 한 줄로** 붙인다. 10분 계획도 시간이 보여야 한다.
- 축소할 때 시간 글자도 제목과 함께 작아진다.
- 겹쳐서 아주 좁은 블록은 제목을 먼저 보여주고 시간은 숨긴다.

**알아 둘 점**
- 지금 기준: `makePlanBlock`은 블록 높이 44px(`TL_TWO_LINES_PX`) 이상(단계 1에서 앞당겨 고침), `makeEventBlock`은 아직 60분 이상. 남은 일은 짧은 블록의 한 줄 표시, 일정 블록, 끄는 도중 표시 전환, 글자 크기 설정 반영이다.
- 5번 요청의 원인: `.tl-time`은 이미 블록 글자 비율을 따른다. 그런데 글자가 줄어드는 조건(`fitBlockText`, 24px 미만)에서는 시간이 아예 그려지지 않는다.
- 두 줄에 필요한 높이는 약 44px이다(기본 글자 크기). 글자 크기 설정이 바뀌면 함께 달라진다. 99px 배율에서 약 27분, 160px 배율에서 약 17분이다.
- 최소 높이는 16px이므로 10분과 5분도 한 줄은 들어간다고 계산했다. **실제 화면으로 확인해야 한다.**
- 확대·축소는 `renderTimeline`으로 다시 그리지만, 길이를 끄는 동안은 다시 그리지 않는다. 끄는 도중에도 표시 방식이 바뀌도록 `beginPlanDrag`도 고친다.
- 제목이 길어 줄바꿈되면 시간이 밀려 잘릴 수 있으니 제목 줄 수를 제한한다.

### 단계 5: 계획 작은 창

**정한 내용**
- 할 일과 연결된 계획도 작은 창에서 이름을 고칠 수 있게 한다. 같은 할 일이므로 가운데 칸과 프로젝트 탭의 이름도 함께 바뀐다.
- 작은 창에 시작·끝 입력 칸을 넣어 드래그 없이 시간을 고치게 한다.
- 가운데 할 일 옆의 시간 글자(`.task-slot`)를 누르면 같은 작은 창이 열린다.

**알아 둘 점**
- 지금 `openPlanPopover`는 빈칸 계획만 입력 칸이고, 연결된 계획은 `h3` 글자다.
- 연결된 계획의 이름은 `PATCH /api/tasks/<id>`의 `content`로 저장하고 `reloadTodayAndTimeline`으로 양쪽을 새로 그린다.
- 시간은 기존 `PATCH /api/time-blocks/<id>`를 쓴다. 서버 검사도 이미 있다.
- `timePopup`은 일정 대화상자 안에 붙어 있어 그대로 못 쓴다. `parseTimeText`, `normalizeTimeInput`만 재사용한다.
- 할 일이 계획 여러 개와 연결돼 있으면 시간 글자는 첫 계획의 창을 연다.
- 블록 안에서 바로 고치는 방식은 끌기와 충돌하므로 쓰지 않는다.
- 작은 창은 시간표 스크롤과 확대 때 닫히면서 저장한다. 시간 칸도 같은 방식으로 저장되는지 시험한다.

## 세션 3

### 단계 6: 번호 없는 할 일

**정한 내용**
- 오늘 탭의 1, 2, 3 번호에서 일부 할 일을 뺄 수 있게 한다. 우선순위 탭(중요도·긴급도 표)과는 관계없다.
- 줄 위치는 그대로 두고 번호만 건너뛴다.

**알아 둘 점**
- `tasks`에 칸을 하나 더한다. `init_db`의 칸 덧붙이기 방식을 쓰고, `EDITABLE_COLUMNS`와 `api_update_task`에도 추가한다.
- `loadTodayTasks`의 `rankCounter`와 `openTasks.length >= 2` 조건이 바뀐다. 번호 있는 할 일 수로 세야 한다.
- `todayTaskOrder`에는 번호 없는 줄도 그대로 넣는다. 그래야 끌기 코드(`taskInsertIndex`, `dropTaskOnList`)를 바꾸지 않아도 된다.
- 번호를 빼고 넣는 버튼의 모양과 위치는 구현할 때 사용자와 정한다. 줄 버튼이 이미 많다.
- 시험: `order_test`, `tmemo_test`의 번호 관련 확인.

### 단계 7: [할 일로 만들기] 버튼

**정한 내용**
- 빈칸에 만든 계획을 자동으로 할 일로 만들지 **않는다.** 자동으로 하면 "점심" 같은 계획이 밀린 할 일, 우선순위 탭, 달력 요약에 쌓인다.
- 빈칸 계획의 작은 창에 [할 일로 만들기] 버튼을 둔다. 필요한 계획만 사용자가 할 일로 만든다.
- 만들어진 할 일은 기본으로 번호 없이 넣는다.
- 기존 계획을 한꺼번에 변환하지 않는다.

**알아 둘 점**
- 이미 있는 "할 일과 연결된 계획" 구조(`time_blocks.task_id`)를 쓴다.
- 할 일 생성과 연결을 서버의 새 API 하나에서 한 거래로 묶어, 중간에 실패해도 반쪽만 남지 않게 한다.
- 만든 뒤 `reloadTodayAndTimeline`으로 양쪽을 새로 그린다.
- 연결 뒤의 동작은 기존과 같다. 계획을 지워도 할 일은 남고, 할 일을 다른 날로 옮기면 계획이 사라진다.

## 세션 4

### 단계 8: 아침 정리 창, 끝낸 날짜 바로잡기

배경: 끝낸 일을 체크하지 못해 밀린 할 일로 뜨는 경우가 많다. 2026-11-06 DB에서 날짜가 있는 완료 할 일 20개 중 10개가 정한 날보다 늦게 체크됐다. 정말 늦게 끝낸 일도 섞여 있다.

**정한 내용**
- 그날 앱을 처음 열 때 밀린 할 일이 있으면 작은 창을 띄운다.
- 줄마다 [끝냈음] [오늘로] [나중에]를 두고, 맨 위에 [전부 끝냈음]을 둔다.
- 정리 창의 [끝냈음]은 **원래 날짜에 끝낸 것**으로 기록한다. 정말 오늘 끝낸 일은 [오늘로]로 옮긴 뒤 체크한다.
- 시간이 지나면 자동 완료하는 기능과 저녁 알림은 만들지 않는다.

**알아 둘 점**
- 지금 `update_task`는 `done_at`을 항상 서버 현재 시각으로 정한다. 원래 날짜를 기록할 길을 새로 만들되, 클라이언트가 아무 시각이나 보내지 못하게 그 할 일의 `date`만 쓰도록 제한한다.
- `list_tasks`는 `done_at` 날짜로도 할 일을 보여준다. 바로잡으면 오늘 목록이 아니라 원래 날짜에 나타나야 한다.
- 하루 한 번 판단에 쓰는 날짜를 설정에 저장한다. 앱을 켜 둔 채 자정을 넘기는 경우(`checkDayRollover`)도 처리한다.
- 하위 단계가 있는 할 일은 `update_task`가 하위까지 함께 완료한다. 원래 날짜 기록이 하위 단계에도 맞는지 확인한다.
- [나중에]를 누른 날은 다시 띄우지 않는다.

## 세션 5

### 단계 9: Ctrl+Z

**정한 범위: 1단계 중에서도 위험이 낮은 동작만.** 앱을 켜 둔 동안만 기록하고, 오늘 탭에서만 작동한다. 글자 입력 칸에서는 평소처럼 글자만 되돌린다.

| 포함 | 되돌리는 방법 |
|---|---|
| 계획 옮기기·길이 변경·시간 수정 | 이전 시작·끝 값으로 PATCH |
| 계획 만들기 | 그 계획을 DELETE |
| 계획 이름 변경 | 이전 제목으로 PATCH |
| 할 일 이름 변경 | 이전 내용으로 PATCH |
| 오늘 할 일 순서 변경 (같은 목록 안에서만) | 이전 순서로 PUT |
| 하위 단계 없는 할 일 체크 | 체크 해제 |
| 번호 빼기·넣기 | 반대로 PATCH |

| 제외 | 이유 |
|---|---|
| 할 일 날짜 이동 ("내일로" 등) | 순서가 비워지고 연결된 계획도 지워진다 |
| 다른 날짜의 할 일을 끌어와서 만든 계획, 다른 목록에서 끌어온 순서 변경 | 날짜 변경이 함께 일어난다 |
| 체크 해제 되돌리기 | 원래 끝낸 시각을 복원할 수 없다 |
| 하위 단계 있는 할 일 완료 | 하위 단계까지 함께 바뀐다 |
| 할 일 삭제, 계획 삭제 | 삭제하면 번호가 바뀌거나 연결된 내용까지 복원해야 한다 |
| [할 일로 만들기], 정리 창의 동작 | 여러 곳을 함께 바꾼다 |
| Google 일정의 모든 동작, 반복 일정, 노트 | 처음부터 제외하기로 정했다 |

**알아 둘 점**
- 범위가 좁아서 DB 변경 기록 방식은 필요 없다. 화면에서 "되돌리는 요청"을 기록해 두면 된다.
- 되돌릴 대상이 이미 없으면(404) 알림을 띄우고 그 기록을 버린다.
- 끄는 중, 작은 창을 연 중, 대화상자를 연 중에는 작동하지 않게 한다.
- 무엇을 되돌렸는지 알림으로 보여준다.
- 기록은 최근 20개 정도만 둔다.

## 이번 묶음에서 하지 않는 것

**app.js 분리.** 이번 위험은 파일 길이가 아니라 할 일과 계획의 연결에서 나오므로 이번 기능에는 필요 없다. 하게 된다면 다음과 같이 한다.
- 시기: 이 기능들을 며칠 써 본 뒤, 친구들에게 나눠 주기 전 정밀 검토와 묶어서 한다.
- 방법: 기능 수정과 섞지 않고 코드 이동만 담은 별도 커밋으로 한다. 일반 `<script>` 여러 개로 나누면 코드 수정이 거의 없다.
- 함정: `calendar.render()`가 파일 중간에서 실행되므로 불러오는 순서를 지켜야 한다.
