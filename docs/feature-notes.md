# 기능별 구현 기록과 결정 이유

> [PLAN.md](../PLAN.md)의 "Google Calendar 연동 설계" 절 "알려진 함정" 목록은 기능을 더하며 기록이 쌓여 길어졌다. 그중 9단계(줄 버튼) 이후의 항목을 이 문서로 옮겼다. 각 항목은 기능을 어떻게 구현했는지, 왜 그렇게 정했는지, 알려진 한계가 무엇인지를 적은 것이다. 같은 목록의 앞쪽 항목(Google 연결과 초기 구현의 함정)은 [google-calendar.md](google-calendar.md)에 있다. 옮기기만 했고 내용은 바꾸지 않았다.

## 알려진 함정에서 이어지는 기록

- **줄 버튼은 마우스를 올려야 보인다 (9단계).** `makeTaskRow`가 "내일로/빼기/+ 하위/삭제"와 마감일이 없는 단계의 "마감일" 버튼을 `.task-actions` 묶음에 넣고, CSS가 평소에는 `display: none`, 줄에 마우스를 올리거나 키보드로 들어가면(`:hover`, `:focus-within`) 보이게 한다. 마감일이 정해진 단계는 알약(칩)이 항상 보이고, 지우기(✕)만 hover 때 나타난다. 처음에는 버튼 묶음을 줄 위에 겹쳐 띄우는 방식을 썼는데 마감일 알약을 반쯤 가려서, 줄 안에 두고 나타날 때 다른 것을 왼쪽으로 조금 밀어내는 방식으로 바꿨다. 터치 화면에서는 hover가 없어 불편하겠지만 이 프로그램은 데스크톱 전용이다.
- **글자 간격(자간) 슬라이더 (9단계).** 글꼴이 마음에 든 사용자가 "Canva처럼 글자 간 간격을 조정할 수 있나"고 물어서 설정 탭에 `글자 간격` 슬라이더를 더했다. 기본값은 0.015em(사용자가 정함. 0이 글꼴 기본). `em`은 글자 크기의 몇 배라는 단위라서 글자 크기 슬라이더를 바꿔도 비율이 유지된다. CSS는 `body`가 아니라 **모든 요소(`*`)에 직접** `letter-spacing: var(--letter-spacing)`을 적는다. body에만 적으면 em이 body 글자 크기(14px) 기준으로 한 번 계산된 값이 그대로 상속되어 제목 같은 큰 글자에는 비율이 맞지 않고, 입력 칸과 버튼은 브라우저가 기본으로 자간을 고정해두기 때문이다. 슬라이더 정의의 `unit`("px" 또는 "em")을 `applySettings`가 CSS 변수에 붙인다. 행간(`line-height`)은 만들지 않았다. 필요해지면 같은 방식으로 한 줄 더하면 된다.
- **키보드 화살표 이동 (9단계).** 사용자가 "Ctrl+화살표와 그냥 화살표 중 어느 쪽이 나은가"를 물어서 **그냥 화살표(←/→)** 로 정했다. Ctrl+화살표는 글자 칸에서 "단어 단위 이동"이고 윈도우 단축키와도 겹칠 수 있으며 두 키를 눌러야 해서 느리다. 대신 화살표를 자기 용도로 쓰는 곳에서는 건드리지 않는다: 모달 창이 열려 있을 때, 글자 입력칸/선택 칸/슬라이더 등에 포커스가 있을 때(`arrowKeysBelongToElement`). 체크박스와 버튼은 화살표를 안 쓰므로 방금 클릭해서 포커스가 남아 있어도 이동한다. Ctrl, Alt, Shift, Win과 함께 누른 조합은 건드리지 않고 비워뒀다(나중에 다른 기능에 쓸 수 있다). ↑/↓는 화면 스크롤용이라 쓰지 않는다. 캘린더 탭에서는 `calendar.prev()/next()`가 지금 보기에 맞는 만큼 움직이고, 오늘 탭에서는 ◀ ▶ 버튼과 같은 동작을 한다. 프로젝트, 설정 탭에서는 아무 일도 하지 않는다. 진짜 키 입력(`Input.dispatchKeyEvent`)으로 정상 이동과 막혀야 하는 8가지 상황을 확인했다.
- **긴 종일 일정 제목 처리 (9단계).** 사용자와 상의해서 "종일 일정은 줄바꿈, 시간 있는 일정은 한 줄 유지, 둘 다 툴팁"으로 정했다. 종일 일정은 마감, 시험처럼 놓치면 안 되는 것들이라 끝까지 읽을 가치가 크고, 하루에 한두 개라 두 줄이 되어도 칸이 크게 늘지 않는다(월간 칸 높이는 원래 "일정이 차지하는 높이"에 맞춰 자란다). 시간 있는 일정은 하루에 여러 개 쌓이므로 "한 화면에 많이 보기"를 위해 한 줄로 둔다. 구현: `#calendar-view`에 `wrap-all-day` 클래스를 붙였다 떼는 방식이고(`settings.json`의 `wrapAllDay`, 기본 true), CSS는 FullCalendar가 일정 블록과 제목에 걸어둔 `white-space: nowrap`과 `overflow: hidden`을 푼다. 한글은 `word-break: keep-all`로 단어 중간에서 끊기지 않게 했다. 툴팁은 FullCalendar의 `eventDidMount`에서 `title` 속성으로 단다. 사용자 말로는 두 줄로도 부족한 제목은 거의 없다. 실제 화면 확인에서 두 줄을 넘은 것은 일부러 만든 아주 긴 제목(3줄)뿐이었다.
- **글자 굵기와 종일 일정 여백 (9단계).** 두 글꼴(Google Sans Flex, Noto Sans KR)은 가변 글꼴이라 굵기를 100~900 사이의 아무 숫자로 연속해서 정할 수 있다(400 보통, 700 굵게, 550 같은 중간 값도 가능). 종일 일정 제목이 너무 굵어 보인다는 사용자 의견에 따라 700에서 600을 거쳐 **550**으로 낮췄다. 값은 `style.css`의 `--all-day-weight` 한 줄이고, 글자 앞 여백(`padding: 1px 5px`, 처음 7px에서 사용자가 5px로 정함)도 같이 줬다. 굵기를 바꿔가며 나란히 비교하고 싶으면, 같은 일정을 굵기별로 복제해서 그리는 방법이 편하다. 
- **글꼴이 둘이라 생기는 두 가지 문제 (9단계).** (1) 시간(Google Sans Flex)과 한글 제목(Noto Sans KR)은 글꼴마다 위아래 여백 계산이 달라서, 한 줄의 상자들을 가운데 맞춤(`align-items: center`)하면 한글이 섞인 제목이 1.5px쯤 아래로 처져 보였다(영문만 있는 제목은 정확했다). 달력의 시간 있는 일정(`.fc-daygrid-dot-event`)과 오늘 탭 일정(`.today-event`)을 **글자 기준선 맞춤(`align-items: baseline`)** 으로 바꾸고, 색 점만 `align-self: center`로 가운데에 뒀다. 기준선 차이를 직접 재서 모든 일정이 0.00px임을 확인했다. 앞으로 두 글꼴이 섞인 줄을 새로 만들 때도 같은 방식을 쓴다. (2) 새 글꼴과 글자 간격 0.015em 때문에 글자가 조금 넓어져서 오늘 탭의 시간(`09:00–10:00`)이 가운데 대시에서 두 줄로 꺾였다. `white-space: nowrap`과 `min-width: 7.5em`으로 고쳤다. 글꼴이나 자간을 바꾼 뒤에는 폭을 고정해둔 칸이 꺾이지 않는지 확인한다.
- **글꼴 (9단계): 영문/숫자는 Google Sans Flex, 한글은 Noto Sans KR.** 사용자가 Google Calendar의 글꼴(일정 추가 창)이 마음에 든다고 했다. Google Calendar가 쓰는 Google Sans는 비공개라서 쓸 수 없고, 모양이 비슷한 Google Sans Flex(2025년 11월 공개, SIL Open Font License)를 썼다. 이 글꼴에는 한글이 없어서 한글은 Noto Sans KR(역시 OFL)이 맡는다. 글꼴 이름을 `--font`에 "앞에서부터 차례로 시도, 없는 글자만 다음 글꼴" 순서로 적어서 이렇게 나뉜다. Google Calendar가 한글에 어떤 글꼴을 쓰는지는 확인하지 못했다. 파일은 npm의 fontsource 패키지에서 받아 `static/fonts/`에 넣었다(인터넷이 끊겨도 같은 모양으로 보이게, FullCalendar와 같은 이유). 영문은 용량을 줄이려고 `latin`, `latin-ext`만(약 77KB), 한글은 글자 조각 124개(합계 3.8MB)를 넣었고 브라우저가 화면에 쓰이는 조각만 불러온다. 각 폴더의 `LICENSE.txt`는 OFL 원문이므로 지우지 않는다. 글꼴을 바꾸고 싶으면 `--font` 한 줄과 `static/fonts/`만 고치면 된다.
- **Pomodoro 타이머 (11단계).** 사용자가 "설정은 설정 탭에서만 바꾸게 하는 것이 낫다"고 해서 위젯은 단순하게 두었다. 설계의 핵심 세 가지: (1) **시간은 "끝나는 시각" 기준**이다. 1초마다 1씩 줄이는 방식은 창이 늦게 그려지거나 컴퓨터가 느려지면 시간이 밀리므로, 시작할 때 `endTime = Date.now() + 남은 시간`을 정해두고 매번 `endTime - Date.now()`로 남은 시간을 계산한다(`pomodoroRemainingMs`). 멈춘 동안에는 `remainingMs`에 남은 시간을 저장한다. (2) **시계는 Web Worker에게 맡긴다.** 공부하는 동안 창을 뒤로 보내거나 최소화해 두는 일이 많은데, 브라우저는 보이지 않는 페이지의 `setInterval`을 크게 늦춘다(오래 가려져 있으면 1분에 한 번까지). 화면과 따로 도는 Worker(`Blob`으로 만든 작은 스크립트)가 0.25초마다 신호를 보내게 했고, Worker를 못 만들면 `setInterval`로 대신한다. 창이 다시 보일 때(`visibilitychange`)도 바로 한 번 확인한다. 이 "최소화된 창에서 제때 울리는지"는 헤드리스 브라우저로는 확인할 수 없어서 실제 창에서 한 번 써보며 확인해야 한다. (3) **소리는 WebAudio로 직접 만든다**(`OscillatorNode`로 "딩" 3음, 소리 파일 없음). 브라우저는 사용자가 아무것도 누르지 않았는데 나는 소리를 막으므로, ▶를 누를 때 `AudioContext`를 미리 만들어 깨워 둔다(`unlockPomodoroAudio`). 집중이 끝나면 올라가는 음(660→880→1320Hz), 휴식이 끝나면 내려오는 음(1320→990→660Hz)이다. 단계가 끝나도 다음 단계를 자동으로 시작하지 않은 이유는, 자리를 비운 사이 시간이 계속 흘러 휴식이 끝나도 모르는 것보다는 멈춰서 기다리는 쪽이 예측하기 쉽기 때문이다. (4) **끌어서 옮기기 (사용자 요청).** 메모리나 CPU 부담은 거의 없다. 끄는 동안 하는 일은 위젯 하나의 `left`/`top` 값 두 개를 바꾸는 것뿐이고, 새로 불러오는 라이브러리도 없다. 포인터 이벤트(`pointerdown/move/up`, 마우스·터치·펜 공용)와 `setPointerCapture`(마우스가 위젯 밖으로 빠르게 나가도 계속 이 위젯이 이벤트를 받게 함)를 쓴다. 4px 이상 움직여야 끌기로 보아서 클릭하다 흔들린 것은 무시하고, 버튼 위에서는 끌기가 시작되지 않는다. 놓은 뒤에 한 번만 저장한다. 서버(`clean_settings`)는 숫자가 아니거나 ±20000을 넘는 위치를 버리고, 실제 화면 안으로 맞추는 일은 화면(`clampPomodoroPosition`)이 한다.
- **우선순위 탭 (12단계).** Claude Code가 처음 제안한 설계(★ 중요 표시 + 마감일로 긴급 자동 계산 + 4칸)를 사용자가 "연속적으로 좌표평면에 올리면 좋겠다, 오늘 탭이 아니라 이 탭 오른쪽에 평가 안 한 목록을 두고 -5~5로 평가하자"로 바꿨고, 글자 겹침 걱정에는 "11×11 격자에 축을 관통시켜 한 칸에 넣자"는 아이디어를 냈다. 결정과 이유: (1) **두 축 모두 직접 끌어서 정한다.** 점 하나를 놓으면 중요도와 긴급도가 한 번에 정해진다. 단점은 "긴급"이 시간이 지나면 낡는다는 것이라서 마감일(D-숫자)을 같이 보여 줘서 사용자가 보고 고치게 했다. 마감일로 점이 저절로 움직이게 하는 것은 써보고 필요하면 추가한다. (2) **값은 정수 -3~3(처음엔 -5~5였다), 저장은 `tasks`의 `importance`, `urgency` 두 칸**이다. 연속값(소수)이 아니라 정수인 것은 칸에 놓는 방식이기 때문이다. 범위는 서버의 `database.PRIORITY_LIMIT` 한 곳에서 정하고(화면의 `PRIORITY_RANGE`는 같은 값), 범위를 줄일 때를 대비해 `init_db`가 옛 값을 새 범위 안으로 맞춘다(`MAX(-3, MIN(3, 값))`, 이미 범위 안이면 변화 없음). 기존 DB에는 `ALTER TABLE`로 칸만 덧붙인다(`PRAGMA table_info`로 확인, 기존 데이터는 그대로). 두 값은 항상 함께 보내야 하고(둘 다 정수이거나 둘 다 null), 서버가 범위, 정수 여부(bool 제외)를 검사한다(`parse_priority`). (3) **끌어다 놓기는 라이브러리 없이 포인터 이벤트로 직접 만들었다.** 끌기를 시작하면 이름표를 복사한 `ghost`가 마우스를 따라다니고(`pointer-events: none`이라 그 아래 칸을 `document.elementFromPoint`로 찾을 수 있다), 놓은 자리가 칸이면 그 칸의 `data-urgency`, `data-importance`를 읽어 저장하고, 오른쪽 목록이면 평가를 취소한다. 4px 이상 움직여야 끌기로 본다. 화면 위/아래 끝에서는 스크롤한다. 저장은 화면에 먼저 반영하고(낙관적 갱신) 실패하면 서버 값으로 되돌린다. (4) **칸은 이름표를 담는 상자**라서 한 칸에 여러 개가 들어가면 줄 높이가 늘어난다(`grid-auto-rows: minmax(40px, auto)`). 칸 폭이 약 70px로 좁아서 이름표 이름은 두 줄까지 보이게 했고(`-webkit-line-clamp: 2`), 마감일 글자는 칸 안에서는 빼고 빨간 테두리로 대신했다. (5) **클릭 메뉴**는 끌기 없이 놓았을 때(4px 미만 이동) 이름표 아래에 뜨는 `position: fixed` 상자다. 메뉴 밖의 `pointerdown`(capture 단계)에서 닫는데, 그때 "방금 닫힌 메뉴가 누구 것이었나"를 기억해 두었다가 같은 이름표를 다시 클릭한 경우에는 되열지 않는다(없으면 닫자마자 다시 열려 닫을 방법이 어색하다). 완료는 화면에서 먼저 치우고 서버에 저장하며 실패하면 서버 값으로 되돌린다. 요청은 "할 일 끝내기, 매트릭스에서 지우기"였고, "지우기"는 할 일 삭제가 아니라 평가 취소(목록으로 되돌리기)로 해석했다. (6) 처음에 구역 이름 색 클래스(`.q-now` 등)를 칸에도 같은 이름으로 써서 이름표 글자가 물드는 버그가 있었다. 이름 줄 안으로 선택자 범위를 좁혀 고쳤고 테스트에 넣었다.

- **일정 창의 Enter 키 구현.** 시간칸 자신의 `keydown`이 Enter를 처리하고(`commitTimeInput`으로 확정한 뒤 `blur()`로 타이핑 모드를 끝낸다), 일정 창 전체의 Enter는 `document`의 `keydown` 하나가 맡는다. 이 핸들러는 일정 창이 열려 있을 때만 동작하고, 시간칸(`.time-field`)과 `BUTTON`/`SELECT`/`TEXTAREA`에서는 물러나며, 날짜 칸은 `blur()`만, 그 밖(제목 칸, 체크박스, 빈 곳)은 `saveEvent()`를 부른다. 시간칸에서 Enter를 `preventDefault`하면 브라우저가 Enter에 보내 주던 `change` 이벤트도 사라지므로, 값을 확정할 때 우리가 `fireTimeChange`로 직접 알린다(마지막으로 알린 값을 `dataset.committed`에 기억해서 같은 값은 다시 알리지 않는다). 확정하면 `blur()`로 포커스가 내려가고, 포커스가 없는 상태에서 누른 다음 Enter는 `body`로 가므로 `document` 수준에서 받아야 한다. 테스트 중 가짜 Google에 "일정 수정" 기능이 없어서 기존 일정 수정 저장이 502로 실패하는 것을 발견했고(앱 문제가 아니라 테스트용 가짜의 한계), 가짜에 수정 기능을 추가해 끝까지 검증했다. 헤드리스 브라우저가 가끔 몇 십 초씩 멈추는 현상도 있었는데 같은 단계에서 재현되지 않아 환경 탓으로 판단했다(화면 잠금 등으로 창이 가려진 상태가 되면 입력 처리가 늦어진다).
- **일정 창의 길이 유지와 길이 버튼.** 기억하는 값은 `eventDurationMs`(끝 − 시작, 밀리초) 하나다. 창을 열 때, 끝 날짜/시간을 고칠 때, 종일 스위치를 바꿀 때 `updateDurationFromFields`가 칸에서 다시 읽고, 시작 날짜/시간이 바뀔 때 `moveEndWithStart`가 `끝 = 시작 + eventDurationMs`로 끝 칸을 채운다(끝 칸을 코드로 채울 때는 `change` 이벤트를 보내지 않아서 길이가 다시 계산되지 않는다). 시간칸은 직접 타이핑하면 브라우저가 칸을 떠날 때 `change`를 보내 주지만, 방향키와 선택창이 값을 바꿀 때는 코드가 `change`를 직접 보낸다. 종일 일정은 "며칠"을 `Math.round(ms / 86400000)`으로 정수로 맞춰서 서머타임 같은 1시간 오차를 없앤다. 길이 버튼은 `eventDurationMs`를 정하고 `moveEndWithStart`를 부른다. 33가지 입력(타이핑, 방향키, 선택창, 날짜 변경, 자정 넘김, 종일, 기존 일정 수정, 저장 값)으로 확인했다.

(2) **함정 1: FullCalendar가 알려주는 "현재 날짜"(`calendar.getDate()`)는 이동할 때마다 보이는 기간의 시작일(이전 달 날짜일 수 있다)로 바뀐다.** 그래서 `dateIncrement`(한 달씩 이동)에 맡기면 12월에서 "다음"을 눌러도 12월에 머물고 "이전"은 두 달씩 건너뛰었다(15번/30번 연속 이동으로 확인). 해결: `calendar.prev()`/`next()`를 월간 보기에서는 **보고 있는 달(`shownMonthDate`: 보이는 기간 시작일 + 6일. 그 주에는 반드시 1일이 있어서)을 기준으로 직접 한 달씩 옮기는 함수**로 바꿔 끼웠다. 이전/다음 버튼과 키보드 ←/→가 모두 이 두 메서드를 부르므로 한꺼번에 고쳐진다. (6) 화면 위·아래 50px 안쪽으로 가면 페이지가 스크롤된다(폴더가 많으면 목표 폴더가 화면 밖일 수 있어서). Esc로 취소한다. (7) **빈틈 메우기와 미끄러짐:** 카드가 다른 열로 튀지 않게 열을 기억해 두는 규칙(위의 "프로젝트 카드 배치") 때문에, 카드가 빠져도 남은 카드는 제 열에 머물러 빈칸이 남았다. 그래서 카드가 빠지거나 들어온 폴더들(`repackFolderIds`)의 기억만 지우고 처음부터 다시 쌓는다(`renderProjects(options)`). 다른 폴더의 카드는 기억이 남아 있어서 움직이지 않는다. 움직임은 **FLIP 기법**(First: 옛 위치를 재고 → Last: 새 위치에 실제로 놓고 → Invert: transform으로 옛 위치에 있는 것처럼 밀어 두고 → Play: transform을 풀면 transition이 새 위치까지 움직여 줌)이다(`snapshotProjectCards`, `slideProjectCards`). 카드는 이미 새 위치에 있어서 애니메이션이 끊겨도 화면이 어긋나지 않고, 끝나면 임시 스타일을 모두 지운다(`transitionend`와 0.6초 뒤 정리를 함께 걸어 둠). 문서 기준 위치로 재서 스크롤이 조금 변해도 어긋나지 않는다. 화면 17개(재현, 미끄러지는 중, 다시 쌓임, 삭제, 수정 창에서 폴더 변경, 움직임 줄이기)로 확인했다.

- **시간 입력칸을 직접 만든 이유 (13단계 이후).** 브라우저 기본 시간칸(`<input type="time">`)은 한국어 환경에서 "오전/오후 → 시 → 분" 칸으로 나뉘어 있어서, 칸을 누르면 맨 앞의 "오전"이 선택되고 거기에 숫자를 쳐도 아무 일도 안 일어난다(실제 브라우저 엔진으로 확인했다). 시계 아이콘의 선택창은 분이 00, 01, 02 … 1분 단위로 나온다. `step` 속성으로 선택창의 분 열을 줄일 수 있을지는 확인하지 않았다. 그와 상관없이 첫 번째 요청("칸을 누르면 바로 타이핑")은 칸 나누기 방식을 유지하는 한 해결되지 않는다. 그래서 글자 칸(`type="text"`) + 직접 만든 선택창으로 바꿨다. 같은 `id`(`event-start-time`, `event-end-time`)를 유지해서 저장 코드의 변화를 최소화했다. 핵심: (1) **글자를 읽는 함수 `parseTimeText`** 가 `오전/오후/am/pm`을 떼어 내고, `시`, `.`, 전각 콜론을 `:`로 통일하고 `분`을 지운 뒤 `9:30`, `14`, `930`/`1430`(세네 자리 숫자) 세 모양으로 읽는다. 오전/오후가 붙어 있어도 시가 13 이상이면 이미 24시간제로 보고 무시한다("오후 14:00"). 37가지 입력을 표로 검증했다. (2) 칸을 누르면 `select()`로 전체 선택하는데, 포커스 직후 마우스를 떼면 브라우저가 선택을 풀어 버려서 그 첫 `mouseup`만 막는다. (3) 선택창은 일정 창(`<dialog>`) 안에 하나만 만들어 두 칸이 같이 쓴다. 모달 창 밖(`body`)에 만들면 창 뒤에 가려지기 때문이다. `position: fixed`라서 창 가장자리에 잘리지 않고, 아래가 모자라면 위로 뜬다. 선택창을 누를 때 `mousedown`을 막아 시간칸의 포커스를 유지한다. (4) 저장할 때 `readTimeFields`가 칸의 글자를 한 번 더 읽어서, 칸을 떠나지 않고 바로 저장 버튼을 눌러도 정확한 시각이 전달된다(테스트로 확인). (5) Esc는 선택창이 열려 있을 때 선택창만 닫는다. (6) 시간 표시를 24시간제(`14:30`)로 통일했다. 달력, 오늘 탭의 일정 시각이 모두 24시간제라서 맞췄고, `오후 2시`처럼 써도 읽는다.
- **사용 중 불편해서 고친 세 가지 (13단계 이후).** (1) **이름 고치기**: 할 일 줄(`makeTaskRow`)에 이름을 고치는 기능이 아예 없었다(서버의 PATCH `content`는 이미 있었다). 프로젝트 카드와 오늘 탭이 같은 함수로 줄을 만들기 때문에 거기에 한 번만 넣어서 모든 곳에 적용했다. 이름 자리를 `<input>`으로 바꿔치기(`replaceWith`)하고, Enter나 blur는 저장, Esc는 취소이다. Enter로 저장이 끝나 입력 칸이 사라질 때 생기는 blur가 한 번 더 저장하지 않게 `finished` 표시를 둔다. 한글을 조합하는 중의 Enter(`isComposing`)는 글자를 확정하는 키라서 무시한다. (4) **WebView 임시 폴더 누적**: pywebview는 기본(`private_mode=True`)으로 실행마다 `%TEMP%\tmpXXXX\EBWebView`(십수 MB)를 새로 만들고 종료 때 지우려다 `WinError 32`(웹뷰 프로세스가 파일을 아직 쥐고 있다)로 실패해 쌓였다(13일 만에 10개, 156MB). `webview.start(storage_path=%LOCALAPPDATA%\StudyFlow\webview_profile)`로 **고정된 전용 폴더**를 쓰게 했다: 지우기가 실패해도 다음에 같은 폴더를 다시 쓰므로 늘지 않는다. **일부러 `private_mode=False`로 바꾸지 않았다.** 그러면 pywebview가 서버 포트를 고정값 42001로 바꿔서 그 포트가 이미 쓰이면 앱이 안 뜨고, 무작위 포트보다 추측하기 쉬워진다. **이 폴더는 종료 때 pywebview가 통째로 지우므로 반드시 전용 폴더여야 한다**(내 데이터가 든 폴더를 넣으면 안 된다). 프로젝트 안이 아니라 `%LOCALAPPDATA%`에 둔 것은 클라우드 동기화나 Git에 섞이지 않게 하려는 것이다. 실제 앱으로 정상 종료와 강제 종료(작업 관리자에서 끝내기와 같다) 직후 재실행이 모두 잘 되는 것을 확인했다. (5) **자정 넘김**: 오늘 탭을 켜 둔 채 자정이 지나면 `todayText`가 탭을 열 때만 갱신되어 어제가 계속 "오늘 할 일"로 보이고 빨간 현재 시각 줄도 사라졌다. `checkDayRollover`가 1분마다(오늘 탭이 열려 있을 때)와 창이 다시 보일 때 날짜가 바뀌었는지 보고, 바뀌었으면 `loadToday()`를 다시 부른다(탭을 다시 여는 것과 같은 경로). 어제를 보고 있었으면 새 오늘로 따라가고, 다른 날을 보고 있었으면 그 날짜를 그대로 둔다(그 날이 새 오늘이 되면 "오늘 할 일"로 바뀐다). **메모나 수정 칸에 글자를 쓰는 중이거나 시간표를 끄는 중(`isTimelineBusy`)에는 건드리지 않고 다음 확인으로 미룬다**(쓰다가 다음 날의 빈 메모 칸으로 바뀌면 안 되므로. 할 일 입력 칸은 화면을 다시 그려도 지워지지 않으니 제외). 브라우저의 `Date`를 앞당기는 화면 시험(`rollover_test`)을 먼저 만들어 고치기 전에 6건이 실패하는 것을 확인했다. (6) **이중 실행 방지**(`single_instance.py`): 바로가기를 두 번 누르면 창이 둘 뜨고 `settings.json`(창이 들고 있는 값을 통째로 저장한다), `events_cache.json`, `token.json`을 서로 덮어쓴다. `msvcrt.locking`으로 `studyflow.lock`의 첫 1바이트를 잠가 두고(프로그램이 끝나면 비정상 종료여도 윈도우가 풀어 준다), 이미 잠겨 있으면 안내 상자만 띄우고 끝낸다. 로그 파일을 여는 것보다 먼저 한다(켜져 있는 쪽의 로그를 지우지 않으려고). 잠금 파일을 아예 못 만들면 막지 않고 켠다. 잠금은 죽은 프로세스의 것이 **몇 초 늦게 풀릴 수 있어서** 안내 상자에 "방금 닫았다면 몇 초 뒤에"라고 적었다. 실제 앱으로 두 번째 실행이 서버도 웹뷰도 만들지 않고 첫 번째는 영향이 없는 것을 확인했다. 알려진 한계: 두 번째 실행이 첫 번째 창을 앞으로 가져오지는 않는다(안내만 한다). **그 뒤 같은 날 마무리한 것**: 이전에 쌓인 Temp의 옛 `tmp*\EBWebView` 폴더 10개(약 111MB)는 사용자에게 확인받고 지웠다. DOMPurify는 3.1.6에서 3.4.17로 올렸다(위 "노트 탭" 항목). `notes_backup/`에는 0바이트 파일 1개뿐이어서 그것과 빈 폴더를 지웠다(오래된 노트 백업을 자동으로 지우는 코드는 쌓여서 문제가 될 때 넣는다). 이 기획서(PLAN.md)는 너무 길어져서 `docs/`로 나눴다. **일부러 안 한 것**: `app.js` 분할(잘 동작하고 시험이 있어서 위험이 이득보다 크다. 기능을 더 추가할 때 같이 한다). 확인으로 알게 된 것: 가상환경의 `pythonw.exe`는 실제 파이썬을 자식 프로세스로 띄우는 껍데기라서, 프로세스를 찾거나 끌 때는 자식을 봐야 한다.
